## 4.1 模块划分与总体调用关系（统稿骨架，供参考）

本系统按职责划分为五个模块：认证与权限模块、工单业务模块、智能分析模块、相似问题检索模块、统计与报告模块。各模块之间通过服务层接口调用，路由层不直接编写模型调用或文本计算逻辑。

后端采用三层结构：接口层（`app/api/routes/`）负责参数接收、身份校验与响应封装；服务层（`app/services/`）承载工单状态机、智能分析、相似检索等业务规则；数据层（`app/models/`、`app/db/`）通过 SQLAlchemy 访问 SQLite。前端 Vue 3 通过 `/api/v1` 调用后端，开发环境由 Vite 代理转发。

一次“提交反馈”的调用顺序为：用户端提交 → 工单接口落库（状态 `PENDING_ASSIGNMENT`）→ 智能分析服务调用模型 → 结果校验后回写工单标题、分类、摘要 → 相似检索服务以标题与摘要为输入查找历史工单 → 管理员在工作台看到整理后的工单并分配负责人。其中智能分析失败不回滚工单创建，保证主流程可用。

> 配图建议：用 draw.io 画“浏览器 → FastAPI 路由 → 服务层 → 模型/数据库”的模块图；时序图用 PlantUML 或 draw.io 画上面五步。

## 4.2 数据库设计（2 号填写，此处只列与智能分析相关的部分）

智能分析结果独立存放在 `analysis_results` 表，与 `tickets` 为一对多关系：一条工单可保留多次分析结果，便于对比提示词版本效果；工单上只保存人工最终确认的标题、分类与摘要，避免模型结果覆盖人工修改。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | 主键、自增 | 分析记录编号 |
| `ticket_id` | INTEGER | 外键 → `tickets.id`，索引 | 所属工单 |
| `generated_title` | VARCHAR(200) | 非空 | 模型生成的标题 |
| `suggested_category` | ENUM | 非空 | 建议分类，取值同工单分类枚举 |
| `generated_summary` | TEXT | 非空 | 生成的摘要 |
| `keywords_json` | TEXT | 可空 | 关键词数组的 JSON 文本 |
| `confidence` | FLOAT | 可空 | 置信度 0~1 |
| `model_name` | VARCHAR(100) | 可空 | 模型标识，如 `deepseek-chat` |
| `raw_response` | TEXT | 可空 | 调用信封：状态、提示词版本、耗时、原始返回片段 |
| `created_at` | DATETIME | 默认当前时间 | 生成时间 |

设计说明：

1. 采用“结果表 + 工单表”分离，模型建议与人工结论各存一份，统计“人工修改率”时有依据。
2. `raw_response` 保存 JSON 信封而非裸文本，既保留追溯能力，又避免为状态、耗时单独加列。
3. 失败的分析不写入本表（`suggested_category` 非空，强行填默认值会污染分类统计），改为在 `ticket_records` 写一条 `action=AI_ANALYSIS_FAILED` 的记录，保证有痕迹且不破坏约束。
4. 未新增数据库迁移脚本，开发阶段沿用 `Base.metadata.create_all` 自动建表；表结构变更需团队确认后统一处理。

## 4.3 接口设计（草稿，详见 `docs/api-conventions.md` 第 7 节）

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/v1/tickets/{id}/analysis?force=&apply=` | 登录且工单可见 | 执行智能整理，可复用历史结果 |
| GET | `/api/v1/tickets/{id}/analysis` | 登录且工单可见 | 读取最近一次结果 |
| POST | `/api/v1/analysis/preview` | 登录 | 提交前预览，不建单、不写库 |

统一响应沿用 `{code, message, data}`。智能分析特有的约定：模型失败返回 HTTP 200 + `data.status=FAILED`，不使用 5xx；只有“未配置/已关闭”才返回 503/50300，因为它属于部署配置问题而非业务结果。

## 4.4 智能分析模块详细设计（正文，可直接使用）

### 4.4.1 模块职责与设计目标

智能分析模块负责把用户提交的口语化反馈整理成结构化信息，为后续分配、检索和统计提供输入。具体职责包括四项：

1. **结构化整理**：生成简短标题、问题分类、摘要和关键词；
2. **模型接入**：封装大模型 HTTP 调用，处理超时、限流、认证失败等异常；
3. **结果校验**：把不可信的模型输出收敛为可入库的固定结构；
4. **失败降级**：模型不可用时保留原始反馈，转人工分类，不阻塞工单主流程。

设计遵循三条原则：

- **模型是增强而非主流程**：工单先落库，分析只是补充建议，任何模型故障都不能导致提交失败；
- **提示词是请求，校验是兜底**：提示词要求 JSON 与固定分类，服务端仍逐字段校验、截断、映射，不能假设模型一定听话；
- **人工结论优先**：模型结果写入独立结果表，工单上的标题、分类、摘要可由管理员随时修改，重新分析需显式触发。

### 4.4.2 处理流程

一次分析请求的处理流程如下：

```text
客户端 POST /tickets/{id}/analysis
        │
        ▼
① 身份与可见性校验（USER 本人 / AGENT 被分配 / ADMIN 全部）
        │ 不可见 → 404
        ▼
② force=false 且已有历史结果 → 直接返回 cached=true（不调用模型、不产生费用）
        │
        ▼
③ 组装提示词：系统提示词 + 功能模块 + 用户描述（超长截断至 4000 字）
        │
        ▼
④ 调用模型（OpenAI 兼容 /chat/completions，温度 0.2，JSON 模式，超时 30s）
        │
        ├─ 超时/429/5xx → 退避重试 1 次
        │
        ▼
⑤ 解析响应：剥离代码块 → 定位首个完整 JSON 对象 → json.loads
        │
        ▼
⑥ 归一化校验：标题/摘要截断、分类别名映射、关键词去重限量、置信度截断到 0~1
        │
        ├─ 分类缺失或非法 → FAILED，转人工
        ▼
⑦ 判定状态：置信度 ≥ 0.6 且无修正 → SUCCESS；否则 DEGRADED
        │
        ▼
⑧ 持久化：写 analysis_results；apply=true 时回写工单标题/分类/摘要
        │
        ▼
⑨ 写处理记录（AI_ANALYSIS / AI_ANALYSIS_FAILED），返回统一响应
```

流程中的关键取舍：

- 第 ② 步的缓存复用避免重复扣费，管理员需要重新整理时显式传 `force=true`；
- 第 ④ 步把温度设为 0.2，分类任务需要稳定而非多样；
- 第 ⑥ 步的“分类别名映射”是实测发现的问题：模型常返回“账号登录”而不是 `ACCOUNT_LOGIN`，直接按枚举校验会误判失败，因此在服务端做一次中英文映射；
- 第 ⑦ 步引入 `DEGRADED` 中间态，比“成功/失败”二分更贴近实际：结果可用但需要人看一眼。

### 4.4.3 输入输出契约

模型输入由两部分组成。系统提示词固定分类体系、输出格式和硬性规则；用户消息只包含功能模块与反馈原文：

```text
功能模块：账号中心
用户描述：修改密码后一直无法登录，重新安装也没有解决。
（描述是否被截断：否）
请按系统提示中的 JSON 契约输出结果。
```

模型必须返回如下 JSON（字段、长度、取值范围均在提示词中声明）：

```json
{
  "title": "修改密码后无法登录",
  "category": "ACCOUNT_LOGIN",
  "summary": "用户修改密码后无法登录，重装后仍未解决，影响正常使用。",
  "keywords": ["密码修改", "无法登录"],
  "confidence": 0.92,
  "reason": "故障发生在修改密码之后，现象为登录失败"
}
```

服务端对外返回的字段在模型字段基础上增加运行信息：

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | `SUCCESS`/`DEGRADED`/`FAILED` | 结果状态，前端据此决定提示文案 |
| `title` / `summary` / `keywords` | string / string / array | 归一化后的结果 |
| `category` / `category_label` | 枚举 / 中文名 | 建议分类及其展示名 |
| `confidence` | float 或 null | 模型自评置信度 |
| `model_name` / `prompt_version` | string | 模型与提示词版本，用于追溯 |
| `needs_manual_review` | bool | 是否需要人工确认分类 |
| `applied` | bool | 是否已写回工单 |
| `cached` | bool | 是否为历史结果复用 |
| `error` | string 或 null | 失败原因，形如 `TIMEOUT: 模型服务响应超时` |
| `elapsed_ms` | int | 本次调用耗时 |

### 4.4.4 提示词设计

提示词分为四部分，存放在 `analysis_prompts.py` 中单独维护，并用 `PROMPT_VERSION` 标识版本。

**（1）角色与任务**：明确“企业客服工单系统的反馈整理助手”，任务是把口语化反馈整理为标题、分类、摘要、关键词，避免模型自由发挥成客服回复。

**（2）分类体系**：五类固定分类，每类给出“判定要点 + 典型说法”，而不是只给分类名。例如 `FEATURE_SUGGESTION` 的描述是“希望新增或改进功能，属于需求而非故障”，并强调“用户明确在提需求时必须归为建议类，不能归为功能异常”。分类数量固定，避免类别无限扩张导致统计口径失控。

**（3）输出契约**：逐个字段说明含义、长度和取值范围，要求“只输出一个 JSON 对象，不要 Markdown 代码块、解释文字或多余字段”。同时给出一个完整示例，示例特意体现“只复述用户已提供的信息”。

**（4）硬性规则**：禁止编造错误码、版本号、时间、金额；信息不足时选择最接近分类并降低置信度；多问题并存时按主要诉求分类并在摘要中说明；摘要用第三人称、不写客服话术、不给处理方案。

工程参数：温度 0.2、`response_format={"type":"json_object"}`、最大输出 800 tokens、输入描述截断至 4000 字、超时 30 秒、失败重试 1 次。

迭代方法：先固定 25~30 条覆盖五类的测试集并人工标注标准分类，每次只改提示词的一处，回测分类准确率与标题可用率，记录版本变化。**（待填：首轮 v1.0 准确率 __%，v1.1 调整 __ 后 __%，测试集 __ 条。）**

### 4.4.5 结果校验与归一化

模型输出被视为不可信输入，服务端依次执行以下校验：

| 校验项 | 处理方式 | 失败后果 |
|---|---|---|
| 代码块包裹 | 正则剥离 ```json 围栏 | 继续解析 |
| 前后夹带解释 | 从首个 `{` 起做括号配平扫描，提取完整对象 | 解析失败 → `BAD_FORMAT` |
| JSON 语法 | `json.loads`，禁止尾逗号、注释 | 解析失败 → `BAD_FORMAT` |
| 标题为空/超长 | 为空用原话前 20 字兜底；超 40 字截断 | 记录 `issues`，降级 |
| 分类缺失/非法 | 先按中英文别名映射；仍失败则判 `FAILED` | 转人工分类 |
| 摘要超长 | 截断至 200 字 | 降级 |
| 关键词 | 支持字符串或数组，去重、单个截断 20 字、最多 6 个 | 忽略多余部分 |
| 置信度 | 非数字置空，超出范围截断到 0~1 | 参与降级判定 |

括号配平扫描而不是简单的 `text[text.find("{"):text.rfind("}")]`，是为了避免模型在 JSON 之后又输出一段带花括号的解释，导致截取范围错误。这一细节在报告中可作为“健壮性设计”的例证。

### 4.4.6 异常处理与失败降级

模型调用层的异常被统一包装为 `LLMCallError`，携带 `kind`、`message`、`retryable`、`status_code` 四个属性，按“是否值得重试”分类处理：

| kind | 触发条件 | 是否重试 | 说明 |
|---|---|---|---|
| `TIMEOUT` | 连接或读取超时 | 是（1 次，0.5s 退避） | 网络抖动、模型排队 |
| `NETWORK` | DNS/连接失败 | 是 | 断网、代理错误 |
| `RATE_LIMIT` | HTTP 429 | 是（1s 退避） | 平台限流 |
| `SERVER` | HTTP 5xx | 是 | 平台故障 |
| `AUTH` | HTTP 401/403 | 否 | Key 错误，重试无意义 |
| `HTTP` | 其他 4xx | 否 | 参数或模型名错误 |
| `BAD_RESPONSE`/`EMPTY` | 响应缺字段、内容为空 | 否 | 平台返回结构异常 |
| `BAD_FORMAT` | 解析或分类校验失败 | 否 | 提示词问题，记录原始文本 |

降级后的系统行为：

1. 工单标题、分类、摘要保持原值（新建工单为“待智能整理”、分类为空），**不写入任何猜测值**；
2. 写入一条 `action=AI_ANALYSIS_FAILED` 的处理记录，内容包含错误类型与“等待人工分类”，处理人和管理员可在详情页看到；
3. 接口返回 HTTP 200 与 `status=FAILED`，前端提示“已保存，请人工选择分类”，而不是报“提交失败”；
4. 错误信息只保留类型与简短原因，不返回模型原始响应、不记录 Key、不打印用户完整描述，避免日志泄露隐私。

“未配置密钥”属于部署问题，由 FastAPI 依赖层直接返回 503/50300，避免每次请求都触发一次必然失败的调用。

### 4.4.7 与其它模块的协作

| 协作对象 | 接口/字段 | 约定 |
|---|---|---|
| 工单模块（2 号） | `tickets.title/category/summary`、`ticket_records.action` | 分析默认写回工单；如需“只出建议”，传 `apply=false`，由工单模块写 |
| 相似检索（4 号） | 分析结果 `title + summary + keywords` | 检索以整理后的文本为输入，相似度只表示“值得参考”，是否同一问题由处理人确认 |
| 用户端（5 号） | `POST /analysis/preview` | 提交前预览，用户可改标题；预览失败不阻止提交 |
| 管理端（6 号） | `status`、`confidence`、`needs_manual_review` | 看板展示“待人工确认”数量；统计口径由程序计算，模型不参与 |
| 分析报告（3 号） | 真实工单统计 + 典型案例 | 报告文字由模型生成，数字必须来自程序统计，禁止模型自行推断 |

### 4.4.8 关键实现说明

- **配置独立**：`analysis_config.py` 只读取 `ANALYSIS_*` 环境变量，不修改公共 `core/config.py`，减少与 1 号的冲突；配置在请求时读取，保证 `.env` 已加载。
- **模型可替换**：通过 `ChatModel` 协议抽象“输入提示词、返回文本”，真实模型与离线 `MockChatModel` 实现同一接口，测试与无密钥演示都通过依赖注入替换，无需改业务代码。
- **可测试性**：`run_analysis()` 不接触数据库，输入模型、配置和文本即可返回结构化结果，便于单元测试；落库与回写放在 `analyse_ticket()`，用 FakeModel 即可覆盖成功、降级、失败、越权等场景。
- **成本控制**：默认复用历史结果；输入截断；`max_tokens=800`；单次调用约 500~1500 tokens，课程演示成本可忽略。

### 4.4.10 局限与改进方向

1. 五类分类是固定集合，遇到“退款/发票”等新业务需要人工扩展枚举与提示词，缺少自动发现新类别的能力；
2. 置信度是模型自评，未做校准，只能作为“是否需要人工看一眼”的粗粒度信号；
3. 未接入向量检索，相似问题完全依赖 4 号的 TF-IDF 模块，长文本语义相近但用词不同的情况召回有限；
4. 未做提示词缓存（相同描述重复提交仍会调用模型），后续可按 `description` 哈希缓存结果；
5. 未接入流式输出，页面需等待完整结果，长文本场景体验一般。

## 4.7 异常处理与失败降级（3 号，可合并进 4.4 或单列）

全系统异常分为四层：

| 层次 | 典型异常 | 处理方式 | 用户可见结果 |
|---|---|---|---|
| 参数层 | 描述过短、分类非法 | Pydantic 校验 → 422/42200 | 表单错误提示 |
| 权限层 | 未登录、越权、工单不可见 | 401/40100、404/40400 | 跳登录页或“工单不存在” |
| 业务层 | 非法状态转换 | 409/40900 | 提示当前状态不允许 |
| 外部依赖层 | 模型超时、限流、返回格式错误 | 降级 + 处理记录 | 200 + `FAILED`，提示人工分类 |

降级设计的三条约束：不丢数据（原始反馈已落库）、不误导（不填猜测分类）、可追溯（处理记录 + `raw_response` 信封）。

本章给出了系统的模块划分、数据库与接口设计，重点说明了智能分析模块的处理流程、提示词设计、结构化输出校验与失败降级机制。设计上把模型定位为“增强能力”，通过固定分类体系、JSON 契约、服务端校验和降级策略，把不可控的模型输出约束在可控范围内，保证工单主流程在模型故障时仍然可用。下一章将介绍系统的实现与测试过程。
