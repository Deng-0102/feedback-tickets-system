### 4.3 数据表为什么没改

`analysis_results` 表是 1 号预留的，字段够用：`generated_title`、`suggested_category`、`generated_summary`、`keywords_json`、`confidence`、`model_name`、`raw_response`。`raw_response` 里存的是 JSON 信封（状态、提示词版本、耗时、原始返回），这样不用加字段就能追溯每次调用的过程。

失败时**不写分析表**（该表要求分类非空），改为写一条 `action=AI_ANALYSIS_FAILED` 的处理记录。答辩时这是加分点：说明你为什么“不轻易改共享表结构”。

## 6. 提示词怎么迭代（报告里要写方法，不是玄学）

1. **固定分类体系**：五类写死在提示词和枚举里，模型只能选，不能造。分类边界写“判定要点 + 典型说法”，比只给分类名有效。
2. **固定输出契约**：字段、长度、取值范围全部写进提示词，同时用 Pydantic 校验。提示词是“请求”，校验是“兜底”。
3. **给一个好例子**：一个高质量 few-shot 比十句规则管用；例子里要体现“只复述、不编造”。
4. **调低温度**：`ANALYSIS_TEMPERATURE=0.2`，分类任务不需要创造性。
5. **开 JSON 模式**：`response_format={"type":"json_object"}`，能显著减少前后废话。
6. **版本化**：每次改提示词改 `PROMPT_VERSION`，数据库里每条结果都记了版本，出问题能回溯。
7. **量化验证**：固定测试集，每次改完重跑，记录准确率，不要凭感觉说“好像变好了”。

## 7. 失败降级策略（答辩必问）

| 错误类型 | 触发场景 | 接口返回 | 系统行为 | 用户/处理人看到 |
|---|---|---|---|---|
| `TIMEOUT` | 模型超过 30 秒 | 200 + `status=FAILED` | 自动重试 1 次；仍失败则保留原反馈 | “已保存，请人工选择分类” |
| `NETWORK` | 断网、DNS 失败 | 同上 | 同上 | 同上 |
| `AUTH` | Key 错误/过期 | 200 + `FAILED` | **不重试**，避免无意义请求 | 同上（管理员看日志排查） |
| `RATE_LIMIT` | 429 限流 | 200 + `FAILED` | 退避 0.5s/1s 重试 | 同上 |
| `SERVER` | 5xx | 200 + `FAILED` | 重试 1 次 | 同上 |
| `BAD_FORMAT` | 返回非 JSON、分类非法 | 200 + `FAILED` | 不重试，记录原始文本 | 同上 |
| 未配置/关闭 | 没填 Key 或 `off` | **503 + 50300** | 依赖层直接拒绝 | 页面提示“智能分析未配置” |

设计原则（写进报告）：**模型是增强，不是主流程**。原始反馈先可靠保存，分析只是给工单加建议；任何模型故障都不能让用户提交失败。所以失败走 200 + 业务状态，而不是 5xx。

## 10. 常见问题

**Q1：`Activate.ps1` 无法加载，因为在此系统上禁止运行脚本**
用 `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass`，或者干脆不激活，直接用 `.\.venv\Scripts\python.exe -m ...`。

**Q2：改了 `.env` 不生效**
`.env` 只在进程启动时读一次，必须重启 uvicorn（`--reload` 不会重读环境变量）。

**Q3：接口返回 503 / 50300**
`ANALYSIS_PROVIDER=off`，或者 `deepseek` 但 `ANALYSIS_API_KEY` 为空。填好 Key 后重启。

**Q4：接口返回 200 但 `status=FAILED`**
看 `data.error` 前缀：`AUTH` 是 Key 问题，`TIMEOUT` 是网络/模型慢，`BAD_FORMAT` 是模型没按 JSON 输出（改提示词或重试）。**工单数据没有丢**，这是设计好的降级。

**Q5：`pytest` 报 `ModuleNotFoundError: app`**
必须在 `backend` 目录下运行；或先 `pip install -e .`。

**Q6：数据库里中文是乱码**
如果是 PowerShell `Invoke-RestMethod` 造成的，是客户端编码问题，不是系统问题——用 Swagger 或 Apifox 测。如果数据库里真是乱码，删掉 `feedback_ticket.db` 重新 seed。

**Q7：模型很慢/经常超时**
调大 `ANALYSIS_TIMEOUT_SECONDS=60`，或换更快的模型（`deepseek-chat` 已比较快）；演示时提前跑一次，避免现场等。

**Q8：能不能不用真实 Key 演示？**
可以，`ANALYSIS_PROVIDER=mock`。但结果里 `model_name=mock-demo-v1`，接口返回 `DEGRADED`，**必须在报告和答辩中说明这是演示模式**，不能当成真实模型效果。团队规则明确禁止把模拟数据当真实实现。

**Q9：为什么失败不写 `analysis_results` 表？**
该表 `suggested_category` 非空，失败时没有可靠分类。硬塞一个默认分类会污染统计。失败改为写 `AI_ANALYSIS_FAILED` 处理记录，既有痕迹又不破坏表约束。

**Q10：老师问“为什么不用微调/向量库”怎么答？**
课程项目数据量小、分类固定五类，提示词 + 结构化输出 + 规则校验的性价比最高；微调需要标注数据和算力，收益在 5 类任务上不明显；相似检索用 TF-IDF 已够（4 号负责），引入向量库会增加部署复杂度。回答时点明“当前规模下的工程取舍”。

**Q11：Swagger 刚登录就返回 401 / 40100，怎么办？**
按顺序排查：

1. `Authorize` 里粘的是不是**带双引号**的 token（从 JSON 里复制时容易一起复制 `"..."`），或者自己加了 `Bearer `——两者都会让请求头变成 `Bearer "eyJ..."` / `Bearer Bearer eyJ...`，后端解不出来；
2. 后端是否重启过：`.env` 里 `SECRET_KEY` 为空时，每次启动都会生成新的随机密钥，旧 token 全部失效。本项目本地 `.env` 已固定 `SECRET_KEY`，正常重启不影响；
3. token 是否超过 120 分钟（`ACCESS_TOKEN_EXPIRE_MINUTES`）。

最省事的验证：重新登录一次，复制 `access_token` 的值（不带引号），重新 Authorize，再点 Execute。

**Q12：Swagger 里 `POST /tickets` 返回的 `id` 是 0，后面按 0 操作都失败？**
那是 **Example Value**（字段示例），不是真实响应。真实响应在下方 **Server response** 里，`data.id` 是数据库自增的正整数（1、2、3…）。如果请求返回 401，说明工单根本没创建成功，也就没有 id；先解决登录问题，再重新提交，或 `GET /api/v1/tickets` 查看已有工单的真实 id。

**Q13：命令行试跑显示“耗时 0 ms”是不是没生效？**
不是。`ANALYSIS_PROVIDER=mock` 是离线演示模型，不走网络，耗时自然是 0；它会在结果里标注 `mock-demo-v1`。要看真实耗时，把 `.env` 改成 `deepseek` 并填 Key，或运行 `--provider deepseek`。
