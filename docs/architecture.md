# 系统架构与第一阶段边界

## 1. 架构目标

系统采用前后端分离的单仓库结构。Vue 负责页面和交互，FastAPI 负责认证、权限、业务规则和数据访问。前端路由守卫只改善使用体验，真正的权限边界始终由后端校验。

```text
浏览器（Vue 3）
        │ HTTP / JSON / Bearer Token
        ▼
FastAPI /api/v1
        │
        ├─ API 路由：参数接收、身份依赖、响应封装
        ├─ Service：工单状态等业务规则
        ├─ Schema：请求与响应模型
        └─ Model / SQLAlchemy：数据持久化
                │
                ▼
        SQLite（开发）/ MySQL（后续部署）
```

后续的智能分类和相似检索优先作为后端 Service 接入，API 层不直接编写模型调用或 TF-IDF 计算逻辑。这样既方便 3、4 号独立开发，也能保证模型失败时工单主流程仍然可用。

## 2. 目录职责

### 后端

| 目录 | 职责 |
|---|---|
| `backend/app/api/routes/` | 路由、依赖注入和 HTTP 层校验 |
| `backend/app/core/` | 配置、令牌、密码和公共权限依赖 |
| `backend/app/models/` | SQLAlchemy 实体与统一枚举 |
| `backend/app/schemas/` | Pydantic 请求和响应结构 |
| `backend/app/services/` | 可复用业务规则，目前包含工单状态机 |
| `backend/app/db/` | 数据库引擎、会话和声明基类 |
| `backend/scripts/` | 可重复执行的本地辅助脚本 |
| `backend/tests/` | API、权限和业务流程测试 |

路由不得复制状态转换规则；需要变更状态时统一复用 `ticket_workflow.py`。密码和令牌逻辑统一由 `core/security.py` 管理。

### 前端

| 目录 | 职责 |
|---|---|
| `frontend/src/api/` | Axios 实例及后端接口封装 |
| `frontend/src/stores/` | Pinia 登录状态与共享状态 |
| `frontend/src/router/` | 页面路由和角色导航守卫 |
| `frontend/src/views/` | 页面级组件 |
| `frontend/src/types/` | 与后端响应一致的 TypeScript 类型 |

页面组件不应自行拼接 API 基地址或重复保存令牌；请求统一通过 `src/api/`，登录状态统一通过 `auth` store。

## 3. 当前数据模型

第一阶段已经建立以下基础实体：

- `User`：用户名、显示名称、密码哈希、角色、启用状态和时间字段。
- `Ticket`：工单编号、标题、描述、摘要、功能模块、分类、状态、提交人、负责人和时间字段。
- `TicketRecord`：操作者、动作、处理内容、原状态、新状态和时间。
- `AnalysisResult`：为后续智能整理预留的分析结果数据。

五类问题使用固定枚举：

| 枚举 | 中文含义 |
|---|---|
| `ACCOUNT_LOGIN` | 账号登录 |
| `FUNCTION_ERROR` | 功能异常 |
| `PERFORMANCE` | 性能问题 |
| `USAGE_CONSULTATION` | 使用咨询 |
| `FEATURE_SUGGESTION` | 功能建议 |

枚举值是前后端和测试之间的协议，不得只在某个页面中单独修改。

## 4. 第一阶段已经覆盖的业务

第一阶段只要求建立可继续扩展的业务骨架：

1. 创建三个角色的演示账号。
2. 用户名和密码登录，签发带有效期的 Bearer Token。
3. 获取当前登录用户并执行前后端角色导航。
4. 普通用户或管理员创建工单。
5. 普通用户只查看自己的工单，处理人员只查看分配给自己的工单，管理员查看全部工单。
6. 管理员把工单分配给有效的处理人员。
7. 按统一状态机更新工单状态并写入处理记录。
8. 对未认证、越权、参数错误和非法状态转换返回统一错误结构。

## 5. 后续阶段范围

以下能力尚未在第一阶段完成：

- 截图上传、补充信息和处理记录页面。
- 调用模型生成标题、摘要和分类建议，以及失败降级和人工修改。
- TF-IDF 与余弦相似度检索、排序和效果验证。
- 管理端完整工单列表、筛选、分类修正和处理记录界面。
- 数量、解决率、处理时长等统计看板。
- 基于真实统计结果生成、展示和导出分析报告。
- 数据库迁移、生产级日志、备份恢复和正式部署。

后续开发必须保证：智能模块失败时反馈仍能保存并进入人工处理；统计值由程序计算，模型只能依据真实统计结果生成文字说明。

## 6. 跨模块约束

- API 前缀固定为 `/api/v1`。
- 时间由后端保存并返回，前端只负责格式化显示。
- 权限必须同时考虑角色和数据归属，不能只隐藏按钮。
- 状态转换必须写入 `TicketRecord`，不能直接静默修改数据库。
- 第一阶段开发环境由 FastAPI 自动建表；进入多人共享数据库前应引入正式迁移流程。
- `.env`、数据库文件、上传文件和真实密钥不得提交到仓库。
